# 跨平台移植指南

## 一、概述

本系统是一套基于应用程序区的通用 Boot 固件升级方案，核心代码位于 `Mod/` 目录下，由四个模块构成：

1. **主升级程序模块**（`Mod/App/app.c`）：升级流程的核心调度单元，运行于应用程序区，负责执行擦除、写入、校验、跳转的完整升级逻辑。
2. **存储区域编程程序模块**（`Mod/External_Interfaces/bsp_flash.c/h`）：擦写与校验的执行单元，负责 Boot 存储区的页擦除、数据写入、读取比对等操作。
3. **底层硬件抽象接口程序模块**（`Mod/External_Interfaces/api_flash_port.c/h`）：跨平台适配层，将 Flash 加解锁、写入、擦除、中断控制等操作抽象为统一接口。
4. **Boot 程序存放模块**（`Mod/BOOT1.c`）：由 `bin2c` 工具将 Boot 固件的 `.bin` 文件转换生成的 C 数组文件。

**移植目标**：只需实现 `api_flash_port.c` 中的 6 个接口函数，并在 `api_flash_port.h` 中配置平台相关的宏定义，即可将本升级系统运行在任何嵌入式平台上。

---

## 二、目录结构

### Mod/ 文件职责

```
Mod/
├── App/
│   ├── app.c                  # boot_update() 主入口，升级流程控制
│   ├── app.h                  # APP_START_ADDR / BOOT_START_ADDR 定义（由用户提供）
├── External_Interfaces/
│   ├── api_flash_port.h       # 配置宏定义（所有 HAL_xxx 宏，用户必须修改）
│   ├── api_flash_port.c       # 跨平台接口实现（用户必须实现，模板为空壳）
│   ├── bsp_flash.h            # 板级支持包头文件（一般不需要修改）
│   ├── bsp_flash.c            # 板级支持包实现（一般不需要修改）
├── BOOT1.c                    # bin2c 生成的 Boot 镜像数组（复制替换即可）
```

### 各文件详细说明

| 文件 | 说明 | 移植者需要修改？ |
|------|------|:---:|
| `app.c` | 封装了完整的升级流程：擦除所有 Boot 页 → 写入新固件 → 校验数据 → （可选）设置跳转标志 → 系统复位。**不需要修改** | 否 |
| `app.h` | 声明 `boot_update()` 函数。通过 `#error` 机制强制要求在编译时定义 `APP_START_ADDR` 和 `BOOT_START_ADDR` | 否 |
| `api_flash_port.h` | 定义所有与硬件平台相关的宏（Flash 地址范围、页大小、总线位宽等）以及 `FlashBandwidthType_t` 类型别名 | **是** |
| `api_flash_port.c` | 提供空壳函数，移植者需填充 6 个硬件操作接口 | **是** |
| `bsp_flash.h` | 声明 `bsp_flash_write()/read()/page_erase()/cmp_flash()` 等上层接口 | 否 |
| `bsp_flash.c` | 基于 `api_flash_port.c` 接口实现的 Flash 读写擦逻辑。包含地址对齐校验、写入循环、尾部散数据填充等通用逻辑 | 否 |
| `BOOT1.c` | 由 `bin2c` 工具生成的二进制数组文件，数组名固定为 `bin_buf`，附带长度常量 `bin_buf_elem_len` 和 `bin_buf_byte_len` | 替换即可 |

## 三、移植步骤

### 第一步：复制 Mod/ 目录

将 `Mod/` 文件夹完整复制到目标工程中。保持目录结构不变：

```
目标工程/
├── Mod/
│   ├── App/
│   ├── External_Interfaces/
│   └── BOOT1.c
```

### 第二步：配置宏定义（api_flash_port.h）

以下宏定义必须在 `api_flash_port.h` 中根据目标平台配置。`#error` 预处理指令会确保每个必需的宏都已被定义。

| 宏名 | 说明 | 示例值（STM32F103） | 必须 |
|------|------|-------------------|:----:|
| `HAL_FLASH_BASE_ADDR` | Flash 起始地址 | `0x08000000UL` | ✅ |
| `HAL_FLASH_END_ADDR` | Flash 结束地址 | `0x0807FFFFUL` | ✅ |
| `HAL_FLASH_PAGE_SIZE` | Flash 页大小（字节） | `1 * 2048` | ✅ |
| `HAL_MIN_WRITE_BAYE` | 最小写入字节数，必须与 `api_flash_write()` 一次写入的字节数一致 | `4` | ✅ |
| `HAL_BAND_WIDTH` | 总线位宽（单位：字节）。支持 1/2/4/8，决定了 `FlashBandwidthType_t` 的类型 | `4` | ✅ |
| `ENABLE_GOTO_FLAG` | （可选宏开关）启用跳转标志功能。定义后编译包含 GOTO_FLAG 代码，取消定义则跳过 | 定义或取消 | ❌ |
| `HAL_GOTO_FLAG_BASE_ADDR` | 跳转标志位存储基地址（仅 `ENABLE_GOTO_FLAG` 启用时需要） | 由用户定义 | ❌ |
| `HAL_GOTO_FLAG_END_ADDR` | 跳转标志位存储结束地址（仅 `ENABLE_GOTO_FLAG` 启用时需要） | 由用户定义 | ❌ |
| `HAL_GOTO_FLAG_OFFSET` | 跳转标志位在存储块中的偏移（以 `FlashBandwidthType_t` 为单位） | `1` | ❌ |
| `HAL_GOTO_FLAG_PARAM` | 写入的标志参数值 | `0x00000005` | ❌ |
| `BOOT_START_ADDR` | Boot 分区起始地址（可以在 `app.h` 中定义，也可在构建系统的全局宏中定义） | `0x08000000UL` | ✅ |
| `APP_START_ADDR` | App 分区起始地址（同上） | `0x08010000UL` | ✅ |

**配置示例（STM32F103ZE，512KB Flash，2KB 页）：**

```c
#define HAL_FLASH_BASE_ADDR      (uint32_t)(0x08000000UL)
#define HAL_FLASH_END_ADDR       (uint32_t)(0x0807FFFFUL)
#define HAL_FLASH_PAGE_SIZE      (1 * 2048)
#define HAL_MIN_WRITE_BAYE        4
#define HAL_BAND_WIDTH            4
```

**注意事项：**

- `HAL_BAND_WIDTH` 决定 `FlashBandwidthType_t` 的类型：1→`uint8_t`，2→`uint16_t`，4→`uint32_t`，8→`uint64_t`。
- `HAL_MIN_WRITE_BAYE` 必须与底层 `api_flash_write()` 一次调用写入的字节数严格一致。例如 STM32F103 的 `HAL_FLASH_Program` 一次写入 1 个 word（4 字节），所以 `HAL_MIN_WRITE_BAYE` 应设为 4。
- `BOOT_START_ADDR` 和 `APP_START_ADDR` 既可在 `app.h` 中定义，也可在编译器的全局宏定义中传入。

### 第三步：实现 api_flash_port.c（核心移植工作）

这是整个移植过程中唯一需要编写代码的步骤。需要实现以下 6 个函数（此外还有 2 个可选的 EEPROM 接口）：

#### 必需实现的接口

**1. `api_flash_lock()` / `api_flash_unlock()`**

Flash 加锁与解锁操作。通常在写入或擦除 Flash 之前需要解锁，操作完成后重新加锁。

```c
// 示例（STM32 HAL）：
void api_flash_lock(void)
{
    HAL_FLASH_Lock();
}

void api_flash_unlock(void)
{
    HAL_FLASH_Unlock();
}
```

**接口语义：**
- 调用时机：由 `bsp_flash_write()` 和 `bsp_flash_page_erase()` 自动调用。
- `unlock` 在写入/擦除前被调用，`lock` 在操作完成后被调用。
- 如果目标平台不需要加解锁，函数体留空即可。

---

**2. `api_flash_write()`**

向指定地址写入 `HAL_MIN_WRITE_BAYE` 字节的数据。

```c
// 函数签名：
RUN_StatusTypeDef api_flash_write(uint32_t addr, FlashBandwidthType_t data[]);

// 示例（STM32 HAL，HAL_BAND_WIDTH=4，HAL_MIN_WRITE_BAYE=4）：
RUN_StatusTypeDef api_flash_write(uint32_t addr, FlashBandwidthType_t data[])
{
    RUN_StatusTypeDef re = RUN_ERROR;
    if (HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD, addr, (uint64_t)data[0]) == HAL_OK)
    {
        re = RUN_OK;
    }
    return re;
}
```

**接口语义：**
- `addr`：写入的目标地址，已由 `bsp_flash_write()` 保证按 `HAL_MIN_WRITE_BAYE` 对齐。
- `data`：待写入数据的缓冲区指针。
- 一次调用必须写入 **恰好 `HAL_MIN_WRITE_BAYE` 字节**。读取 `data[0]` 至 `data[HAL_MIN_WRITE_BAYE/HAL_BAND_WIDTH - 1]`。
- 返回 `RUN_OK` 表示成功，`RUN_ERROR` 表示失败。

---

**3. `api_flash_page_erase()`**

擦除指定地址所在的 Flash 页。

```c
// 函数签名：
RUN_StatusTypeDef api_flash_page_erase(uint32_t addr);

// 示例（STM32 HAL）：
RUN_StatusTypeDef api_flash_page_erase(uint32_t addr)
{
    RUN_StatusTypeDef re = RUN_ERROR;
    uint32_t PageError;
    FLASH_EraseInitTypeDef pEraseInit;
    pEraseInit.Banks       = FLASH_BANK_1;
    pEraseInit.NbPages     = 1;
    pEraseInit.PageAddress = addr;
    pEraseInit.TypeErase   = FLASH_TYPEERASE_PAGES;
    if (HAL_FLASHEx_Erase(&pEraseInit, &PageError) == HAL_OK)
    {
        re = RUN_OK;
    }
    return re;
}
```

**接口语义：**
- `addr`：要擦除的页起始地址。由调用方保证该地址是页对齐的（`addr % HAL_FLASH_PAGE_SIZE == 0`）。
- 一次调用擦除一整页（大小为 `HAL_FLASH_PAGE_SIZE` 字节）。
- 返回 `RUN_OK` 表示成功，`RUN_ERROR` 表示失败。

---

**4. `api_irq_enable()` / `api_irq_disable()`**

全局中断控制。Flash 写入操作期间应关闭中断，防止在写入过程中触发中断导致操作失败。

```c
// 示例（Cortex-M 内核）：
void api_irq_enable(void)
{
    __enable_irq();
}

void api_irq_disable(void)
{
    __disable_irq();
}
```

**接口语义：**
- `bsp_flash_write()` 在写入循环前调用 `disable`，写入完成后调用 `enable`。
- 如果目标平台在 Flash 写入期间不需要关闭中断，函数体留空即可。

---

#### 可选实现的接口

**5. `api_flash_write_eepro()` / `api_flash_page_erase_eepro()`**

EEPROM 操作接口，用于支持模拟 EEPROM 功能的平台。如果目标平台不需要 EEPROM 功能，保持空壳即可。

```c
// 函数签名：
RUN_StatusTypeDef api_flash_write_eepro(uint32_t addr, FlashBandwidthType_t data[]);
RUN_StatusTypeDef api_flash_page_erase_eepro(uint32_t addr);
```

### 第四步：生成 BOOT1.c

使用 `tool/bin2c/bin2c.py` 工具将 Boot 固件的 `.bin` 文件转换为 C 数组。

**操作步骤：**

1. 将编译好的 Boot 固件（`BOOT1.bin`）放入 `tool/bin2c/` 目录。
2. 运行 `bin2c.py`，选择与 `HAL_BAND_WIDTH` 匹配的位宽：
   - `HAL_BAND_WIDTH = 4` → 选择 **32bit**
   - `HAL_BAND_WIDTH = 1` → 选择 **8bit**
   - `HAL_BAND_WIDTH = 2` → 选择 **16bit**
   - `HAL_BAND_WIDTH = 8` → 选择 **64bit**（脚本交互菜单中暂不直接支持，需手动修改脚本）
3. 生成的 `.c` 文件放入 `Mod/` 目录，替换原有的 `BOOT1.c`（文件名可自定义，参考实现中为 `BOOT.c`）。
4. 生成的数组中包含以下符号，与 `app.c` 的 `extern` 声明自动匹配：
   - `bin_buf[]`：固件数据数组
   - `bin_buf_elem_len`：数组元素个数
   - `bin_buf_byte_len`：数组总字节数

**注意事项：**
- `bin2c` 转换时选择的位宽必须与 `HAL_BAND_WIDTH` 一致，否则 `FlashBandwidthType_t` 与数组类型不匹配会导致编译错误。
- 如 `HAL_BAND_WIDTH = 4` 但选用 8bit 转换，数组类型为 `unsigned char`，但 `app.c` 中 `extern const FlashBandwidthType_t bin_buf[]` 会被展开为 `extern const uint32_t bin_buf[]`，类型不匹配。

### 第五步：集成到构建系统

1. 将 `Mod/` 下所有 `.c` 文件加入工程的源文件列表：
   ```
   Mod/App/app.c
   Mod/External_Interfaces/api_flash_port.c
   Mod/External_Interfaces/bsp_flash.c
   Mod/BOOT1.c
   ```

2. 设置头文件包含路径（Include Path），使编译器能找到以下头文件：
   - `Mod/External_Interfaces/`（查找 `api_flash_port.h`、`bsp_flash.h`）
   - `Mod/App/`（查找 `app.h`）

3. 如果使用了 `ENABLE_GOTO_FLAG` 功能，确保相关地址宏已正确配置。

4. 编译工程，确认零错误零警告。

## 四、验证

1. **编译验证**：编译工程，确保零错误零警告。`api_flash_port.h` 中的 `#error` 指令会检查所有必需宏是否已定义。
2. **功能验证**：在应用程序区的适当位置（如收到升级指令后）调用 `boot_update()` 函数。
3. **串口日志检查**：通过串口观察升级流程输出：
   - `"updata start...."` — 升级开始
   - `"Prepare to erase N page"` — 正在擦除 N 个页
   - `"write boot bin in all N..."` — 开始写入 N 个元素
   - `"write ok"` — 写入成功
   - `"cmp ok"` — 校验通过
   - （如启用 `ENABLE_GOTO_FLAG`）`"go to boot"` — 即将复位启动 Boot
4. **复位验证**：升级完成后系统应自动复位（或在启用 GOTO_FLAG 时自动复位），检查 Boot 是否正常启动。
5. **参考实现对照**：可参考 `boot_update_test/app-brp/Mod/` 目录下的 STM32 参考实现，了解完整的移植示例。

## 五、常见问题

**Q: bin2c 转换时选择多少位？**

A: 与 `HAL_BAND_WIDTH` 保持一致。
- `HAL_BAND_WIDTH = 4` → 选择 32bit
- `HAL_BAND_WIDTH = 1` → 选择 8bit
- `HAL_BAND_WIDTH = 2` → 选择 16bit

选择不一致会导致 `FlashBandwidthType_t` 与数组类型不匹配。

---

**Q: 为什么 `api_flash_write()` 要写入 `HAL_MIN_WRITE_BAYE` 字节？**

A: `bsp_flash_write()` 按 `HAL_MIN_WRITE_BAYE` 字节对齐执行写入循环。每次调用 `api_flash_write()` 时，传入的地址已对齐至 `HAL_MIN_WRITE_BAYE` 边界，因此底层函数必须一次完整写入 `HAL_MIN_WRITE_BAYE` 字节。这是写入吞吐量和地址对齐约束共同作用的结果。

---

**Q: `ENABLE_GOTO_FLAG` 必须使用吗？**

A: 不需要。`ENABLE_GOTO_FLAG` 是一个可选的条件编译宏。如果不定义该宏，GOTO_FLAG 相关代码块（标志位读取、写入、校验和系统复位）会被预处理器排除，不会编译进最终固件。GOTO_FLAG 的功能是：升级完成后在指定的 Flash 地址写入一个标志参数，供 Boot 启动时读取判断升级状态。

---

**Q: `HAL_MIN_WRITE_BAYE` 设置多少合适？**

A: 设置为 `api_flash_write()` 一次调用所能写入的字节数。例如：
- STM32F103 的 `HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD, ...)` 一次写入 1 个 word（4 字节），所以 `HAL_MIN_WRITE_BAYE = 4`。
- 如果目标平台的 Flash 控制器允许一次写入 1 个字节，则 `HAL_MIN_WRITE_BAYE = 1`。

---

**Q: `api_flash_port.c` 中的 EEPROM 函数需要实现吗？**

A: 不需要。`api_flash_write_eepro()` 和 `api_flash_page_erase_eepro()` 是预留的可选接口。保持空壳即可，系统不会主动调用这两个函数。

---

**Q: 生成的 `BOOT1.c` 中数组名和变量名是否固定？**

A: 是的。`bin2c.py` 固定输出以下符号，与 `app.c` 中的 `extern` 声明匹配：
- `const FlashBandwidthType_t bin_buf[]`（数组）
- `const unsigned long long bin_buf_elem_len`（元素个数）
- `const unsigned long long bin_buf_byte_len`（总字节数）

如果手动生成 `BOOT1.c`，请确保这些符号名与 `app.c` 的声明一致。

---

## 六、参考实现

`boot_update_test/app-brp/Mod/` 目录下包含了基于 STM32 HAL 的完整参考实现，其中：

- `api_flash_port.c` 实现了基于 STM32 HAL 库的 Flash 操作：
  - `api_flash_lock/unlock` → `HAL_FLASH_Lock/Unlock`
  - `api_flash_write` → `HAL_FLASH_Program(FLASH_TYPEPROGRAM_WORD, ...)`
  - `api_flash_page_erase` → `HAL_FLASHEx_Erase(...)`
  - `api_irq_enable/disable` → `__enable_irq/__disable_irq`
- `api_flash_port.h` 中的宏定义采用了 STM32 标准库提供的常量（`FLASH_BASE`、`FLASH_BANK1_END`）。
- `Mod/App/app.h` 中直接定义了 `BOOT_START_ADDR = 0x8000000` 和 `APP_START_ADDR = 0x8010000`。
- 参考实现中 Boot 镜像数组文件名为 `Mod/BOOT.c`（模板中为 `BOOT1.c`，文件名不影响编译，由 `bin2c` 生成后替换即可）。

将该参考实现与当前模板对比，可以清楚地看到移植者需要提供的代码量极少——只需填充 `api_flash_port.c` 中的 6 个函数并修改 `api_flash_port.h` 中的宏定义即可。
